# Индивидуальный incoming-контекст inbound-провайдера

## Цель

Исправить #1101: PJSIP endpoint провайдера типа `REG_TYPE_INBOUND` и сгенерированный dialplan должны ссылаться на один существующий контекст. Каноническое имя контекста — `<provider.uniqid>-incoming`.

## Поведение

- Каждый включённый `REG_TYPE_INBOUND` получает отдельный `<uniqid>-incoming` независимо от совпадения `host` и `port` с другими провайдерами.
- `generateProviderEndpoint()` записывает `context = <uniqid>-incoming`.
- `extensionGenContexts()` создаёт секцию `[<uniqid>-incoming]` через `IncomingContexts::generate()` и передаёт `uniqid` для выборки маршрутов этого провайдера.
- Endpoint и AOR inbound-провайдера продолжают называться по `username`: имя PJSIP-объекта не обязано совпадать с dialplan-контекстом.
- Контексты `<username>-incoming` и совместимые alias-секции не генерируются.
- Объединение в общий host:port-контекст сохраняется для остальных типов регистрации, которые могут идентифицироваться по IP и не всегда различимы на уровне endpoint.

## Совместимость

Изменение намеренно заменяет ранее генерировавшийся `<username>-incoming` на `<uniqid>-incoming`. Пользовательские dialplan-вставки и модули, которые напрямую ссылаются на старое имя, должны быть обновлены. Автоматический alias не предусмотрен по принятому решению.

## Структура реализации

В `SIPConf` вычисление имени incoming-контекста для одного провайдера должно иметь единый источник истины. Вспомогательный метод возвращает:

- `uniqid` для `REG_TYPE_INBOUND`;
- `uniqid` для одиночного провайдера другого типа;
- нормализованный общий `context_id` для группы другого типа.

`generateProviderEndpoint()` и `extensionGenContexts()` используют одинаковое правило. При обходе dialplan inbound-провайдер обрабатывается отдельно до host:port-группировки, чтобы его маршрут не смешивался с маршрутами соседних провайдеров.

## Проверки

Автоматические тесты должны подтвердить:

1. Одиночный inbound-провайдер получает `<uniqid>-incoming`, даже если `username` отличается от `uniqid`.
2. Два inbound-провайдера с одинаковым `host:port` получают две отдельные секции `<uniqid>-incoming`.
3. `context` каждого inbound endpoint совпадает с реально созданной dialplan-секцией.
4. Для обычных провайдеров существующее поведение сохраняется: одиночный получает индивидуальный контекст, совпадающие `host:port` — общий.
5. `<username>-incoming` для inbound-провайдера отсутствует.

## Обработка ошибок

Пустой `uniqid` не является допустимым состоянием модели и не получает отдельного fallback на `username`. Существующая валидация уникальности `Sip.uniqid` остаётся границей корректности данных.
