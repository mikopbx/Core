# Сторонние модули в маркетплейсе MikoPBX — спецификация шага 1

Дата: 21.09.2026. Статус: на согласовании у владельца.
Охват: сервер релизов и лицензий (mikolicenseserver, модуль `Releases`), контракт между сервером и АТС,
ядро MikoPBX (mikopbx/Core). Кода в документе нет — только требования и точки правок.

## 1. Цель

Принимать в маркетплейс модули сторонних авторов (бесплатные и платные), не проверяя вручную каждый релиз
и не открывая клиентам канал доставки вредоносного кода.

Модуль исполняется внутри АТС с правами root, песочницы нет. Поэтому шаг 1 не обещает «безопасный код».
Он обеспечивает четыре вещи:

1. у каждого стороннего модуля есть известный издатель, и публиковать релизы модуля может только он;
2. файл, который получила АТС, — тот самый файл, который принял сервер;
3. администратор АТС до установки видит, кто издатель и каков уровень доверия;
4. MIKO может отозвать версию, и администраторы установленных АТС об этом узнают.

### Не цели шага 1

| Что | Куда |
|---|---|
| EdDSA-подпись ZIP ключом издателя, удостоверенным MIKO | шаг 2, после пилота |
| Подписанный ответ каталога | шаг 2; нужен только вместе с автоотключением |
| Автоотключение модулей по команде каталога | не планируется |
| Второй способ входа в кабинет издателя (GitLab.com, email+TOTP) | при первом авторе без GitHub |
| Ручное или агентное ревью кода каждого релиза | не планируется |
| Проверка `max_pbx_version` | поле убирается из документации (раздел 6) |
| Режим ядра «установка только из маркетплейса» | запросов не было |
| Публичный канал beta (подписка АТС на предварительные релизы) | когда авторы попросят внешних тестировщиков; значение `beta` в API зарезервировано (4.4) |
| Автоматизация выплат авторам | расчёт вручную по договору |
| Истекающие ссылки на ZIP платных модулей | отдельная задача, касается всех модулей |
| Аудит локального (loopback) доступа к REST ядра | отдельная задача после перепроверки по коду |

## 2. Термины и уровни доверия

**Издатель** — учётная запись автора на сервере, принятая MIKO. Идентичность издателя — числовой ID его
учётной записи GitHub. Место хранения кода с идентичностью не связано: проверки владения репозиторием нет.

| Уровень | `trust_level` | Кто | Условия |
|---|---|---|---|
| Официальный | `official` | MIKO | модуль без издателя в базе |
| Проверенный издатель | `verified` | автор с договором | может быть платным и с закрытым кодом; продаёт MIKO через существующие SKU/feature_id; перед покупателем отвечает MIKO |
| Сообщество | `community` | любой принятый автор | только бесплатные; обязательна ссылка на публичные исходники; «как есть» |

**Первый приём** — единственное ручное действие MIKO на модуль: сотрудник смотрит заявку, первый релиз и
ссылку на исходники (для «сообщества» — что они действительно публичны) и нажимает «принять».
Дальнейшие релизы издатель выпускает сам, MIKO реагирует постфактум отзывом.

## 3. Предусловия

1. На сервере слита ветка унификации записи релизов: оба существующих маршрута записи — тонкие обёртки
   над `MikoLicense\Releases\Library\ReleasePublisher::publish(array $in): array`. На 21.09.2026 эта работа
   не слита и не выкачена. Все серверные проверки этой спецификации
   встают в `publish()` один раз; маршрут издателя — третья обёртка над ним.
2. Имена полей `MINVER`/`MINPBXVER` и формат ответов существующих маршрутов не меняются — это зона задачи
   по депрекации REST API.

## 4. Сервер (mikolicenseserver)

### 4.1. Модель данных

**Новая таблица `Publishers`** (в тенанте MIKO):

| Колонка | Назначение |
|---|---|
| `id` | первичный ключ |
| `github_id` | числовой ID GitHub, уникальный; идентичность издателя |
| `github_login` | логин для отображения, обновляется при входе |
| `name` | публичное имя издателя, показывается в АТС |
| `contact_email` | для связи MIKO с издателем, наружу не отдаётся |
| `support_email` | публичный адрес поддержки, отдаётся в каталоге |
| `trust_level` | `verified` или `community` |
| `status` | `active` или `blocked`; у заблокированного не работают ни токен, ни кабинет |
| `token_hash` | sha256 от токена API; сам токен не хранится |
| `token_created`, `token_last_used` | для аудита и экрана кабинета |

Токен у издателя один. Перевыпуск заменяет `token_hash`, старый токен перестаёт работать сразу.
Несколько токенов с перекрытием сроков не делаем, пока об этом не попросит реальный издатель.

**Новые колонки `ReleasesTypes`:**

| Колонка | Назначение |
|---|---|
| `publisher_id` | ссылка на `Publishers`; `NULL` = официальный модуль MIKO |
| `source_url` | ссылка на исходники; обязательна при `trust_level=community` |

Признак «первый приём пройден» новой колонки не требует: это существующий флаг `ReleasesTypes.released`,
который уже скрывает модуль из каталога, пока он не выставлен. «Принять модуль» = `released=1`.

Существующее текстовое поле `developer` остаётся для официальных модулей. Для сторонних в каталог
отдаётся `Publishers.name`.

**Новые колонки `Releases`:**

| Колонка | Назначение |
|---|---|
| `withdrawn` | пусто / `publisher` / `moderation` |
| `revoke_reason_ru`, `revoke_reason_en` | причина отзыва, заполняется только при `moderation` |

**Новая колонка `ReleasesFiles.sha256`.** У старых релизов пуста.

### 4.2. Аутентификация издателя

- Заголовок `Authorization: Bearer <токен>`, только по HTTPS. Токен — 32 случайных байта в base64url
  с префиксом `mpub_`, чтобы его находили сканеры секретов.
- Сервер сравнивает sha256 токена с `token_hash` через `hash_equals`, проверяет `status=active`,
  обновляет `token_last_used`.
- Токен — только для CI. Паролем кабинета он не служит.
- Существующая HMAC-аутентификация остаётся только у маршрутов MIKO (CI MIKO, TeamCity, 1С, NightBird).
- В журнал не пишутся ни токен, ни его хеш — только `publisher_id`.

### 4.3. Маршруты издателя — `/releases/v1/publisher/*`

Все маршруты работают только с модулями, у которых `ReleasesTypes.publisher_id` равен издателю токена.
Проверка владения — одна функция, вызывается первой в каждом обработчике. Каждое изменяющее действие
пишется в аудит: кто, что, GUID, версия, IP.

| Метод и путь | Действие |
|---|---|
| `GET /modules` | свои модули: GUID, имя, `released`, `trust_level` |
| `GET /modules/{guid}/releases` | свои релизы: версия, состояние, sha256, число скачиваний |
| `POST /modules/{guid}/releases` | загрузить релиз (multipart, см. 4.4) |
| `PATCH /releases/{id}` | править `changelog_ru` / `changelog_en` |
| `POST /releases/{id}/withdraw` | снять свой релиз (`withdrawn=publisher`) |
| `POST /releases/{id}/publish` | перевести свой релиз в `stable`: загруженный как `draft` или снятый самим издателем; только при `released=1`, иначе `409` «ожидает первого приёма» |

Издатель не может: создавать GUID; менять `developer`, уровень доверия, `feature_id`, `product_id`, цену,
`severity`, `source_url`; удалять релиз; возвращать релиз с `withdrawn=moderation`.

Коды ошибок: `401` — токен неверен или издатель заблокирован; `403` — чужой GUID или релиз;
`409` — версия уже существует, не больше предыдущей, или файл этой версии уже лежит в хранилище;
`413` — превышен размер (при превышении лимита nginx ответ придёт его стандартной страницей, не JSON —
оговорить в примере CI); `422` — проверка ZIP
не пройдена, в теле — машинный код причины (`zip_open`, `zip_limits`, `zip_path`, `manifest_missing`,
`manifest_json`, `setup_missing`, `guid_mismatch`, `guid_charset`, `version_mismatch`) либо
`channel_invalid`; `429` — больше 20 загрузок в сутки.

### 4.4. Приём релиза

Поля запроса: `file` (ZIP), `version`, `min_pbx_version`, `changelog_ru`, `changelog_en`, `channel`.

`channel` принимает `draft` (загрузить, не публиковать) и `stable` (опубликовать для всех). Если поле не
передано — `draft`. Значение `beta` зарезервировано и в шаге 1 отклоняется с `422` (`channel_invalid`),
как и любое другое. Поле названо каналом, а не булевым `publish`, намеренно:
запрос разойдётся по CI авторов, и появление канала beta не должно их ломать. Публикация и канал — разные
оси: состояние «не опубликован» и отзыв нужны при любом числе каналов. Проверить релиз до выхода автор
может уже сейчас — ручной установкой ZIP на свою АТС.

Порядок на сервере:

1. Аутентификация, проверка владения GUID, лимит загрузок.
2. Файл принимается во временный каталог. Размер не больше **100 МБ** (одна константа). Лимиты nginx
   (`client_max_body_size`) и PHP (`upload_max_filesize`, `post_max_size`) поднимаются **только** для
   location этого маршрута.
3. Проверка ZIP. Архив на диск **не распаковывается** и ничего из него не исполняется; читаются только
   оглавление и `module.json` через `ZipArchive`:
   - файл открывается как ZIP;
   - суммарный распакованный размер не больше 500 МБ, файлов не больше 20 000;
   - в именах нет `..`, абсолютных путей, записей-симлинков;
   - `module.json` лежит в корне и разбирается как JSON;
   - в оглавлении есть `Setup/PbxExtensionSetup.php` — без него ядро установку прерывает;
   - `moduleUniqueID` совпадает с GUID строки `ReleasesTypes` (не с именем репозитория)
     и проходит `^Module[A-Za-z0-9]{1,60}$`;
   - `version` в манифесте совпадает с полем запроса и строго больше последней версии модуля
     по `version_compare`.
4. Сервер сам считает `sha256`, `md5` и размер. Значения от клиента не принимаются.
5. Сервер кладёт файл на files.miko.ru своей WebDAV-учёткой в отдельную папку издателей по пути,
   вычисляемому из GUID и версии. WebDAV-учётки авторам не выдаются. По ссылкам авторов сервер не ходит.
   Если объект по целевому пути уже существует — это ошибка запроса (`409`), файл не перезаписывается.
   Публичная ссылка для `ReleasesFiles` — непредсказуемая ссылка общего доступа хранилища, как у
   существующих релизов; по GUID и версии она не вычисляется.
6. Вызов `ReleasePublisher::publish()` с нормализованным входом. `sha256` пишется в `ReleasesFiles.sha256`.
7. Сбой на шагах 5–6 удаляет временный файл и только тот объект хранилища, который создал этот запрос;
   релиз не создаётся.

Проверки качества кода (`php -l`, PHPStan, secret-scan, линтер манифеста) выполняются в CI автора и
сервером не дублируются.

### 4.5. Гейт первого приёма — внутри `ReleasePublisher::publish()`

- `released=0`: релиз всегда создаётся скрытым (`prerelease=1`), `channel=stable` игнорируется,
  ответ сообщает «ожидает первого приёма».
- `released=1`: `channel=stable` публикует релиз сразу, `channel=draft` оставляет его скрытым.
- Если у GUID есть `publisher_id`, **создание релизов** через маршруты записи MIKO (HMAC) отклоняется:
  релизы стороннего модуля попадают на сервер только через маршрут издателя. Действия модерации (приём,
  отзыв, `severity`, блокировка издателя) выполняются в VendorCabinet и под этот запрет не подпадают.
- Для модулей без издателя поведение прежнее.

### 4.6. Действия MIKO в VendorCabinet

Расширяются существующие экраны, отдельной роли издателя в VendorCabinet нет:

- завести издателя: GitHub ID, имя, адреса, уровень; выдать первый токен (показывается один раз);
- завести GUID обычным порядком и привязать к издателю, указать `source_url`;
- «принять модуль»: `released=1` и публикация ожидающего релиза;
- отозвать версию: `withdrawn=moderation` и причина ru/en;
- выставить `severity` релизу — как сейчас, только MIKO;
- заблокировать издателя.

Заявка автора приходит письмом или issue. Форму заявки не делаем.

### 4.7. Кабинет издателя (шаг 1б, после API)

Отдельная поверхность, без общей сессии и контроллеров с VendorCabinet. Вход через GitHub OAuth: пускает
только `github_id`, уже заведённый MIKO, со `status=active`. Три экрана — модули, релизы (загрузка, снятие,
возврат), changelog — и кнопка перевыпуска токена. Кабинет ходит только в API издателя, к базе сам не
обращается.

### 4.8. Состояния релиза

| Состояние | `released` | `prerelease` | `withdrawn` | В каталоге | Предупреждение на АТС | Кто публикует |
|---|---|---|---|---|---|---|
| опубликован | 1 | 0 | пусто | да | нет | — |
| ожидает первого приёма | 0 | 1 | пусто | нет (предпросмотр MIKO — да) | нет | MIKO («принять») |
| загружен, не опубликован | 1 | 1 | пусто | нет (предпросмотр MIKO — да) | нет | издатель |
| снят издателем | 1 | любое | `publisher` | нет | нет | издатель |
| отозван модерацией | 1 | любое | `moderation` | нет | да, с причиной | только MIKO |

Правило чтения для всех состояний задано один раз — в 5.1.

Если издатель считает свою версию опасной, он выпускает исправление, а об отзыве просит MIKO.

## 5. Контракт «сервер — АТС»

Общее правило совместимости: поля только добавляются. `md5` и `href` остаются — в эксплуатации тысячи
старых ядер. Ядро трактует отсутствие новых полей как «официальный модуль, старый сервер».

### 5.1. `getAvailableModules`

В каждом элементе `modules[]` добавляются:

| Поле | Значение |
|---|---|
| `trust_level` | `official` / `verified` / `community` |
| `publisher` | публичное имя издателя; для официальных — прежний `developer` |
| `source_url` | ссылка на исходники или `null` |
| `support_email` | адрес поддержки издателя или `null` |

`minSecureVersion` — без изменений.

На верхнем уровне ответа добавляется `revoked`: объект «GUID → список `{version, reason}`», `reason` —
на языке из `LANGUAGE` запроса, с откатом на английский. В `revoked` попадают только релизы с
`withdrawn=moderation`; ядро сопоставляет установленную версию точным совпадением
(`version_compare(…, '==')`). Срок давности не вводится: отзывы редки. Порог пересмотра — 200 записей
в ответе. Поле вынесено из `modules[]` намеренно: модуль,
у которого отозваны все версии, из `modules[]` пропадает, а предупреждение установленным АТС всё равно
нужно. Старые ядра незнакомый ключ игнорируют.

Правило чтения одно для всех маршрутов. Релиз отдаётся клиенту, только если:

- `withdrawn` пусто — без исключений для кого-либо;
- и модуль принят, а релиз опубликован (`released=1`, `prerelease=0`) — **либо** запрос пришёл с адреса из
  существующего на сервере списка адресов предпросмотра владельца каталога (для издателей в каталоге MIKO
  это адреса MIKO).

`prerelease=1` на сервере — не публичный канал beta, а внутренний предпросмотр. Он используется при первом
приёме: сотрудник MIKO ставит ожидающий релиз из каталога на свою АТС до нажатия «принять»; так же видны
релизы `draft` принятых модулей. 4.5 выставляет `prerelease=1` и непринятым, и `draft`-релизам.

Правило реализуется и проверяется тестом **на каждом** маршруте чтения по отдельности, включая
`getModuleLink`: он единственный отдаёт ссылку на файл и адресует релиз по числовому идентификатору,
поэтому обязан применять то же правило сам, а не полагаться на то, что идентификатор скрытого релиза
клиенту неоткуда взять. Маршруты чтения: `getAvailableModules`, `getModuleInfo`,
`getModuleLink`, `ifNewReleaseAvailable`, расчёт `minSecureVersion`. Уже выданная ссылка на файл
отозванной версии продолжает открываться — это принятое ограничение шага 1, файл MIKO удаляет вручную.

### 5.2. `getModuleInfo`

Те же четыре поля на уровне модуля.

### 5.3. `getModuleLink`

В `modules[0]` добавляется `sha256` (64 символа hex в нижнем регистре). Для релизов, загруженных до
шага 1, поле отсутствует или пусто.

Гарантия контракта: `href` — всегда абсолютный `https`-URL, для любых релизов, включая архивные.

## 6. Ядро (mikopbx/Core)

Пишется под текущую структуру ядра. Номера строк — на `develop` от 21.09.2026 (`083ba6727`).
Если маркетплейс позже вынесут в отдельный модуль, пункты 6.4–6.5 переедут вместе с ним,
пункты 6.1–6.3 останутся в ядре: это граница доверия.

### 6.1. Целостность и схема ссылки — конвейер по умолчанию

- `src/PBXCoreREST/Lib/Modules/Pipeline/ModuleDownloadService.php`:
  - `download()` обязан отклонять невалидный URL и любую схему, кроме `https`, до сетевого запроса;
  - `download()` получает необязательный `sha256`; в `verify()` (строки 135–151): если `sha256` передан —
    сверяется `hash_file('sha256')`, иначе прежняя сверка md5. Несовпадение удаляет файл и прерывает
    операцию с отдельным текстом ошибки. Откат на md5 допустим только при отсутствии поля (релизы до
    шага 1). Принятое ограничение: тот, кто способен подменить ответ каталога, может убрать `sha256` и
    вернуть сверку к md5; закрывается подписанным ответом каталога в шаге 2.
- `Pipeline/InstallPipeline.php::phaseAcquireFromRepo()` (строки 221–236): `sha256` берётся из
  `$moduleLink` рядом с `href` и `md5` и передаётся в `download()`.
- `Lib/Modules/DataStructure.php` (строки 472–479): рядом с `md5` описывается `sha256`,
  шаблон `^[a-f0-9]{64}$`.

Аварийный legacy-конвейер (`MODULES_LEGACY_INSTALL_PIPELINE=1`): в `StartDownloadAction.php:72` схема
сужается до `https`. `sha256` туда не добавляется: `WorkerDownloader::checkFile()` общий с загрузкой
прошивки, правка затронула бы обновление системы. Ограничение осознанное.

### 6.2. Набор символов `moduleUniqueID`

`moduleUniqueID` из `module.json` валидируется в `GetMetadataFromModulePackageAction::main()` (строка 95)
до любого использования значения; через это действие проходят оба пути установки, поэтому проверка одна.
Выражение — то же, что уже есть в `StartDownloadAction.php:64`. Оно объявляется один раз: константой и
`pattern` у `uniqid`/`id` в `DataStructure::getParameterDefinitions()` (единственный источник правил
валидации REST); оба действия ссылаются на неё.

Сервер для новых сторонних модулей строже (`^Module…`, п. 4.4). Ядро остаётся мягче, чтобы не сломать
установленные модули.

### 6.3. Источник установки и уровень доверия

В модель `src/Common/Models/PbxExtensionModules.php` добавляются две колонки (свойство с `@Column` —
`UpdateDatabase` добавит их сам, отдельной миграции не нужно):

| Колонка | Значения |
|---|---|
| `installSource` | `marketplace` / `manual` / пусто у ранее установленных |
| `trustLevel` | `official` / `verified` / `community` / пусто |

Заполняет `InstallPipeline::phaseSetupNewVersion()` сразу после успешного дочернего шага `install` — там
же, где уже перечитывается версия (`InstallPipeline.php:462`). Не установщик модуля: строку реестра создаёт
`PbxExtensionSetupBase::registerNewModule()`, он принадлежит коду модуля и переопределяется. Для установки
из репозитория пишутся `marketplace` и `trust_level` из ответа `getModuleInfo`, полученного в
`phaseAcquireFromRepo()`; для пакета — `manual` и пустой уровень. `trustLevel` — снимок на момент
установки: смена уровня издателя на сервере его не обновляет до следующей установки или обновления.
В каталоге и модалке деталей уровень всегда берётся из ответа сервера; колонка нужна списку
установленных. Принятое ограничение шага 1. Список модулей кешируется в Redis
(`getModulesArray()`) — после добавления колонок кеш сбрасывается. Обновление из маркетплейса модуля, когда-то поставленного вручную, меняет источник
на `marketplace`. Пустые значения интерфейс показывает без бейджа.

### 6.4. Интерфейс

- Пути: JS — `sites/admin-cabinet/assets/js/src/PbxExtensionModules/`, шаблоны —
  `src/AdminCabinet/Views/PbxExtensionModules/`.
- В строке каталога колонка автора показывает `publisher`, при его отсутствии — прежний `developer`.
- **Бейдж уровня доверия**: строка каталога (`pbx-extension-module-marketplace.js`, шаблон 361–380),
  модалка деталей (`pbx-extension-module-detail.js::cbAfterGetModuleDetails()`, `moduleDetailsModal.volt`),
  список установленных (`indexTabs/installedTab.volt`, данные из `PbxExtensionModulesController.php:45–69`).
  Для `official` бейджа нет. В модалке деталей дополнительно — имя издателя, ссылка на исходники,
  адрес поддержки.
- **Бейдж «установлен вручную»** — в списке установленных при `installSource=manual`.
- **Окно подтверждения** на базе существующего `moduleInstallModal.volt`:
  - ручной ZIP — сейчас на этом пути подтверждения нет; модалка переиспользуется в
    `pbx-extension-module-install-from-zip.js::checkStatusFileMerging()` перед вызовом
    `ModulesAPI.installFromPackage()`. Текст: модуль не из маркетплейса, исполняется с правами root,
    MIKO его не проверяла;
  - модуль `community` из маркетплейса — отдельного окна нет: в уже существующий
    `openInstallModuleModal()` (`pbx-extension-module-install-from-repo.js`), который показывается перед
    каждой установкой, добавляется ветка текста. Текст: модуль сообщества, MIKO проверяла только издателя при первом приёме, код не проверяется,
    исполняется с правами root, поддержку оказывает издатель.
  Для `official` и `verified` окно не показывается. Ничего не запрещается.
- Новые поля ответа каталога объявляются в `response`-секции `DataStructure`: на сборках с
  `SCHEMA_VALIDATION_STRICT=1` ответы проверяет `ResponseSchemaValidator`.
- Тексты — в `src/Common/Messages/ru/`, перевод скиллом `translations`. JS правится в `assets/js/src/**`
  и транспилируется.

### 6.5. Отзыв версии

Расширяется существующая проверка `src/Core/Workers/Libs/WorkerPrepareAdvice/CheckModulesUpdates.php`.
Она уже раз в сутки читает каталог и сравнивает версии с `minSecureVersion`.

- В `process()` добавляется **отдельный проход** по установленным модулям
  (`PbxExtensionModules::getModulesArray()`), выполняемый до существующего цикла по `modules[]`.
  Существующий цикл для этого непригоден: он пропускает модуль, которого нет в каталоге, и модуль, для
  которого в каталоге нет версии новее, — а это ровно случаи отзыва. Если установленная версия есть в
  `revoked[uniqid]` — совет уровня **`error`** `adv_ModuleVersionRevoked` с именем модуля, версией и
  причиной. Уровень `error` выбран потому, что
  `WorkerNotifyAdministrator` отправляет письмом только его; нового почтового кода нет.
- В списке установленных у строки — пометка «версия отозвана» с причиной. Пометку ставит JS страницы
  модулей по строке `tr.module-row[data-id=…]` из уже загружаемого ответа `getAvailableModules`;
  контроллер и `installedTab.volt` ради этого не меняются. Действия — уже существующие:
  обновление, если в каталоге есть версия новее, и переключатель отключения.
- `minSecureVersion` — без изменений (уровень `warning`).
- Ядро само ничего не отключает. Новая причина отключения в `PbxExtensionState` не вводится.
- Частота проверки не меняется. Худшая задержка от отзыва до письма — около 25 часов (кеш каталога 1 ч +
  кеш совета 24 ч + опрос почтового воркера 1 ч). Принятое ограничение шага 1.
- Отсутствие ключа `revoked` = отзывов нет.

### 6.6. Чистка `max_pbx_version`

Поле нигде не проверяется и реализовываться не будет. Убирается из `DataStructure.php`
(строки 100, 136, 350), из ключей `rest_schema_module_max_pbx_version` во всех языках
`src/Common/Messages/*/RestApi.php` и из DevelopementDocs (`marketplace/licensing.md`, `module-json.md`).
`DataStructure::createFromRepositoryData()`, где живёт строка 100, не имеет вызывающих — удаляется целиком.

## 7. CI автора и документация

- Пример публикации для любого CI: сборка ZIP и один `curl` с Bearer-токеном из секретов CI на
  `POST /releases/v1/publisher/modules/{guid}/releases`. Общий `extension-publish.yml` MIKO сторонним
  авторам не подходит (WebDAV, общий секрет организации) и не меняется.
- Рекомендуемые бесплатные проверки в CI автора: линтер манифеста, `php -l`, PHPStan, secret-scan.
- Страница онбординга в DevelopementDocs: уровни доверия, заявка, первый приём, публикация, отзыв,
  обязанности издателя (адрес поддержки, реакция на инциденты).
- Исправление неверных утверждений документации: `max_pbx_version` и описание способа раздачи файлов
  в `Releases/CLAUDE.md`.
- Шаблон договора для «проверенного издателя» готовит владелец.

## 8. Проверка полноты: пилот `ModuleCalleridSearchCH`, уровень «сообщество»

1. Автор пишет MIKO. MIKO заводит издателя (GitHub ID автора, `community`), GUID
   `ModuleCalleridSearchCH`, `source_url`, выдаёт токен.
2. Автор кладёт токен в секреты CI. CI собирает ZIP и загружает релиз 1.0.0 с `channel=stable`.
3. Сервер проверяет ZIP, считает sha256, кладёт файл в хранилище, создаёт скрытый релиз.
   Ответ: «ожидает первого приёма».
4. MIKO смотрит заявку и публичность исходников, ставит ожидающий релиз из каталога на свою АТС
   (он виден только с адресов предпросмотра MIKO), нажимает «принять». Релиз виден в каталоге.
5. Администратор АТС видит модуль с бейджем «сообщество», издателем и ссылкой на исходники,
   подтверждает окно-предупреждение. Ядро качает файл по `https`, сверяет sha256, ставит модуль,
   пишет `installSource=marketplace`, `trustLevel=community`.
6. Автор выпускает 1.0.1 — релиз выходит сразу, MIKO не участвует.
7. В 1.0.1 найден дефект, роняющий звонки. MIKO отзывает 1.0.1 с причиной. Версия пропадает из каталога;
   АТС с 1.0.1 в течение суток показывают красный совет и отправляют письмо; в списке модулей —
   «версия отозвана». Автор выпускает 1.0.2 — на АТС появляется кнопка обновления.
8. Попытка записать релиз этого GUID через маршруты MIKO или чужим токеном отклоняется.

## 9. Тестирование

- Сервер, юнит: проверка ZIP — по одному случаю на каждый код причины из 4.3, включая zip-бомбу и
  запись-симлинк; владение GUID (свой, чужой, заблокированный издатель); гейт первого приёма; отказ
  маршрутов MIKO для GUID с издателем; правило чтения 5.1 на каждом маршруте, отдельно `getModuleLink` по идентификатору снятого, непринятого
  и `draft`-релиза с постороннего адреса — пусто; непринятые и `draft` видны с адресов предпросмотра;
  `POST /releases/{id}/publish` при непринятом модуле — `409`; `channel=beta` и отсутствующий `channel`;
  состав `revoked`.
- Сервер, перед выкатом: security-ревью несколькими моделями — сервис интернет-ориентированный.
- Ядро, юнит (в контейнере): `verify()` — sha256 совпал, не совпал, отсутствует (откат на md5);
  отказ для `http://`; проверка набора символов идентификатора; проход отзыва в `CheckModulesUpdates` —
  отозвана последняя установленная версия при более старой в каталоге, и модуль, пропавший из каталога.
- Ядро, `tests/api`: ручной ZIP с недопустимым `moduleUniqueID` отклоняется; установленный модуль
  получает `installSource`.
- Ядро, UI: бейджи и оба окна подтверждения; совет об отзыве — на подменённом ответе каталога.
- Сквозной прогон раздела 8 на тестовом стенде до пилота с реальным автором.

## 10. Порядок работ

1. Сервер: слияние ветки унификации (предусловие).
2. Сервер: `Publishers`, новые колонки, токен, маршруты издателя, приём ZIP, гейт, действия в VendorCabinet.
3. Сервер: новые поля чтения (`trust_level`, `publisher`, `source_url`, `support_email`, `sha256`, `revoked`).
4. Ядро — параллельно с п. 2–3, зависит только от раздела 5: пункты 6.1–6.6.
5. Пример CI, онбординг, правка документации.
6. Сквозной прогон и пилот.
7. Кабинет издателя (шаг 1б).

## 11. Требует подтверждения при планировании

- Семантика `ReleasesTypes.released` для официальных модулей MIKO: убедиться, что использование флага как
  признака первого приёма не меняет их поведения.
- Точный состав ответов каталога — выведен из кода потребителей ядра, живым запросом не сверялся.
- Наличие ключей `adv_*` / `ext_*` во всех языках.
- До выката 6.1 живым запросом `getModuleLink` для старого релиза убедиться, что `href` отдаётся по `https`.

## 12. Журнал решений владельца (21.09.2026)

1. Ручной приём — только первый релиз модуля; дальше автоматически, отзыв постфактум.
2. ZIP загружается на сервер MIKO; сервер по ссылкам авторов не ходит.
3. Платные сторонние модули продаёт MIKO; только уровень «проверенный издатель».
4. Отзыв — только предупреждение; автоотключения нет.
5. Сначала API издателя, затем кабинет поверх него; вход через GitHub OAuth; токен только для CI.
6. «Сообщество» обязано дать ссылку на публичные исходники.
7. Издатель — отдельная таблица; токен Bearer, в базе только хеш.
8. Маршрут издателя — новая обёртка над общим `ReleasePublisher::publish()`; существующие маршруты не меняются.
9. Хранилище — files.miko.ru через WebDAV сервера; лимит ZIP 100 МБ.
10. Проверки ZIP на сервере — только целостность и манифест, без распаковки и без `php -l`.
11. Отзыв: `minSecureVersion` для «есть исправление» и список отозванных версий с причиной; выставляет только MIKO.
12. Ручной ZIP: окно-предупреждение, колонка источника, бейдж; запрета нет.
13. `max_pbx_version` убирается из документации.
14. Спецификация ядра пишется под текущую структуру, без ожидания аудита выноса маркетплейса.
15. Отзыв доставляется советом уровня `error`; частота проверки прежняя, задержка до ~25 ч принята.
16. Граница шага 1 (раздел «Не цели») — по умолчанию, явного ответа владельца не было.
17. Выходом релиза управляет поле `channel` (`draft` / `stable`), а не булев `publish`; канал `beta`
    зарезервирован и в шаге 1 не реализуется. Непринятые релизы видны с адресов предпросмотра MIKO для
    проверки при приёме. Признак «принят» — существующий `ReleasesTypes.released`, новой колонки нет.
